# Designer utility: build, persistence and agent interfaces

Date: 27 September 2026. Status: research and proposed boundaries; no runtime, build or hosting changes made.

## Findings from this repository

Stormwatch already separates browser-independent gameplay rules from browser adapters. Both the ordinary game and the artificial benchmark import the same `Game`; the benchmark constructs an artificial level and modifies live state to maintain stress counts. The designer utility should reuse the gameplay engine while remaining a separate application. It should not use the artificial stress fixture as its balance runner. [Architecture](../ARCHITECTURE.md), [game entry](../../src/main.ts), [benchmark](../../src/qa/benchmark.ts)

The production build currently declares **both `index.html` and `qa.html`** as Vite inputs. The Pages workflow builds and uploads the entire `dist` directory. The existing local output contains `qa.html`, a QA JavaScript chunk and the heartbeat worker. This means the current build boundary does not meet the requested exclusion of tooling from deployment. This is source/output inspection, not evidence of an existing remote deployment. [Vite configuration](../../vite.config.ts), [Pages workflow](../../.github/workflows/pages.yml), [QA entry](../../qa.html)

There are also tooling imports in the game entry. Its `window.stormwatch` read-only diagnostic object has an `import.meta.env.DEV` guard; the `?measure` load-report import does not. Recording is statically imported and activated with `?record`. The renderer contains opt-in profiling fields and branches shared with ordinary play. Excluding a separate designer HTML entry will not itself remove these paths. The implementation needs an explicit decision about which ordinary capabilities belong in the release and which diagnostics belong only in local tools. [Game entry](../../src/main.ts), [load report](../../src/qa/load-report.ts), [renderer](../../src/render/battlefield.ts), [recording](../../src/render/recording.ts)

Campaign persistence is managed by the game entry using player profile/save keys; save parsing itself is pure. The utility can reuse progression resolution and validation without writing to the two children's profiles. A utility playtest needs its own attempt lifecycle, storage namespace and synthetic progression scenario. [Game entry](../../src/main.ts), [profile persistence](../../src/persistence/profiles.ts), [save parsing](../../src/persistence/save.ts), [progression](../../src/content/progression.ts)

The repository also has a CLI characterization runner that bundles TypeScript with Rolldown and imports the generated module. Its scripted strategies call the same `Game` commands, fixed-step `tick` and events as the game. Its launch pattern is an existing route for an agent-facing balance runner, but the scenarios reference removed roles/economy and currently fail against the first-map roster. Reuse current strategy tests as policies instead; the [playtest investigation](2026-09-27-designer-utility-playtest.md) records the failed characterization run. [Runner launcher](../../tools/run-challenge-baseline.mjs), [baseline](../../tools/challenge-baseline.ts)

## Relevant platform facts

Vite supports explicit HTML entry points for multi-page builds. A game-only entry graph and an independent utility entry graph can therefore live in the same repository. Vite statically replaces `import.meta.env.DEV`, allowing guarded code to be removed from production; merely naming a mode “development” does not change `NODE_ENV`. Files in `public` are copied into build output even when source code does not import them. Keep drafts, scenario fixtures and utility exports outside `public`. [Vite production build](https://vite.dev/guide/build#multi-page-app), [Vite environment constants and modes](https://vite.dev/guide/env-and-mode), [Vite public assets](https://vite.dev/guide/assets#the-public-directory)

GitHub Pages hosts static HTML, CSS and JavaScript. A custom Actions workflow can publish a selected static artifact; it need not publish the repository tree. Pages cannot host the proposed local repository-writing service. A public source repository remains inspectable independently of the deployed artifact. A client's JavaScript runtime is also inspectable/evaluable through browser tools. Consequently, excluding the utility removes convenient debug controls and shipped tooling; it cannot guarantee that a determined player cannot inspect or alter a local, client-only game. This conclusion is an inference from the hosting and browser execution model. [What GitHub Pages hosts](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Chrome runtime inspection/evaluation](https://chromedevtools.github.io/devtools-protocol/v8/Runtime/)

The File System Access API can let a user select and write a local file, but requires a user gesture/permission and browser capability detection. It should not be the sole persistence mechanism for a utility intended to work across browsers. A downloadable file and a local Node command avoid making this picker a requirement. [Chrome File System Access API](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)

## Proposed boundaries

These are design recommendations, not implemented behavior:

- **Shared runtime:** authored content, content validation/resolution, gameplay rules and ordinary renderer/input components. Both clients and the CLI consume these through explicit interfaces. The gameplay simulation must ship with the game; the utility's runners, automated policies, editor and test fixtures need not.
- **Game application:** normal campaign, profiles, saves, rewards and presentation. Its import graph cannot reach the designer application, automated strategy/search code or file-writing service.
- **Designer application:** a separate local browser page with map/wave registry, resolved settings, spawn timeline, draft editing, progression overrides, isolated playtest and report comparison. It creates ordinary `Game` attempts from selected resolved data; it does not mutate the running campaign or its save keys.
- **Developer runner:** browser-independent scenarios, recorded command schedules, bounded strategy policies/search and structured reports. It exposes the same content/scenario identifiers to UI and CLI. Automated results label the policy, command budget, time horizon and objective rather than asserting universal beatability or fun.
- **Local authoring adapter:** validates, compares and writes selected content variants into version control. Browser storage preserves drafts; a local service or CLI performs explicit promotion to canonical files. It is never part of the game artifact.

Use a dedicated utility Vite config/entry and a separate ignored output directory if a compiled utility is useful. Keep `npm run build` and the Pages artifact game-only. Utility and QA checks can still run in CI before publication, but their outputs must not be inside the uploaded directory. Avoid relying on an obscure URL, a production query parameter or a hidden button as the exclusion mechanism.

## Persisting changes without damaging canonical content

A useful progression is **draft → named variant → comparison → apply to game**. A variant carries a schema version, base content revision/hash, stable map id, wave id/number, changed values and optional intent. Attempts reference an immutable resolved copy of that variant. Editing or restarting it does not alter canonical content; applying it validates the complete resolved configuration and produces a reviewable repository diff. Reject stale promotion when the base content changed instead of silently overwriting it.

Prefer a structured, narrowly scoped local write adapter or CLI importer over arbitrary TypeScript text replacement from a browser. If implemented as a loopback service, permit only known content/variant files, validate payloads and origin, and apply atomic writes. The browser need not have arbitrary filesystem access. A validated export/import command can serve as the simpler first implementation, with direct local “Apply” added behind the same interface. Runtime content should have one source of truth; do not maintain one format for the game and a second independently interpreted copy for the utility.

## Agent navigation and release verification

Expose CLI operations such as list maps/waves, show resolved configuration, validate a variant, simulate a scenario and apply a reviewed variant. Human labels like “map 3 wave 6” should resolve through the campaign registry to stable identifiers; the output should include both. Reports should be structured JSON plus a readable summary, recording content revision, progression overrides, difficulty, seed, policy/actions and outcomes. Browser drafts alone are insufficient for reproducible agent work; named variants and scenarios must be exportable or readable through this interface.

Document the three responsibilities separately in architecture and authoring guidance: gameplay rules, authored map/wave data and utility/instrumentation. Include a short lookup table for map order, ids and source/variant locations. Agent instructions should route balance requests through this registry and distinguish an authored-data change from a new rule or editor feature.

Release acceptance should inspect the **built artifact and dependency graph**, not only source folders: no designer/QA HTML, runner/editor code, writer endpoint, scenario fixtures, QA worker or diagnostic UI. Check that the normal game still boots under the Pages project subpath, while the utility can play the same canonical scenario locally. Verify a saved/promoted variant round-trips, is used by both clients, and changes no campaign profile. No upstream or hosting configuration is needed to perform these local checks.
