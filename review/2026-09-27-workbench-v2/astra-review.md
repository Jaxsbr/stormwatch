# Stormwatch workbench V1: adversarial first-use UX review

Reviewed `src/workbench/main.ts`, `src/workbench/style.css`, `docs/WORKBENCH.md`, `before-desktop.png`, and `before-fresh-desktop.png`. This is a source-informed interface review, not a live usability test. The original screenshot shows an existing draft and a named difficulty candidate. The fresh-load screenshot confirms that the source initializes a fresh session to the third encounter and its final wave: “The Roadwarden's Column,” with 40 enemies and a boss. Both screenshots show the same underlying first-viewport problem.

The user's rejection is justified. The workbench exposes its storage and simulation vocabulary before it helps someone change a game setting. Its capabilities are valuable, but the default presentation asks the owner to become an operator before becoming a designer. V2 should make one small edit and one trustworthy playtest obvious; the existing specialist capabilities should remain available through deliberate disclosure.

## Highest-priority findings

### 1. The interface has no visible first task

**Observation.** In the 1280 × 720 screenshot, nearly the entire viewport is navigation, draft naming/revisions, explanatory prose, and a rhythm/route preview. Neither an editable setting nor Play is visible. The strongest action is “Fork named draft.” The slogan “Author rhythm. Play the consequence. Keep the choice.” does not explain what to do. “Lesson: Unspecified” and “Intended outcome: Unspecified” occupy prime space without helping the first edit. The source puts recipe editing, scenario setup, assistance, preservation, and promotion into one vertical document. The initial guidance message is at the very bottom. Fresh source defaults select the final wave of the third encounter, increasing complexity before the user has chosen it.

**Consequence.** The first decision is about version management, not game design. A user seeking “make this wave a little easier” sees many concepts and no bounded path. They cannot predict how much they must learn before achieving a useful result. Disabled editing before forking compounds this: visible controls look unavailable for reasons the user must infer.

**Improvement.** Introduce a short, visible invitation: “Choose a wave, change a setting, then play it. Changes stay in your local draft.” Start at the first encounter's first wave for a genuinely new session; offer a clear resume choice for saved work. Make **Tune** the initial workspace. Present encounter/wave selection compactly, a small relevant visual preview, and a short set of common fields. Put a single prominent **Save & play** action beside those fields. Create a local working copy as part of the first meaningful edit, with an automatic readable name and optional rename; expose revision history as a secondary action. This preserves the underlying safe draft model without requiring a lesson in branching. Keep promotion deliberate and separate.

**Acceptance check.** With empty browser storage at 1280 × 720, the user can see what this tool does, which wave is selected, at least one editable setting, and the play action without scrolling. Ask a first-time user to “give the first encounter more starting crowns, then try it.” They should complete the task without opening documentation, naming a draft, interpreting an ID, or configuring a scenario. Target one minute; validate with actual observation rather than claiming success from a screenshot.

### 2. Editing and testing do not form a trustworthy loop

**Observation.** Field edits live in DOM inputs until “Validate and save new revision” copies them into `content`. `launch()` builds its `AttemptSession` from `content` and reads only scenario inputs. Therefore a user can change a number and select “Play fresh attempt” while the attempt still uses the previous saved number. Selecting another wave, forking, loading a revision, exporting, or other actions that call `render()` can replace the DOM without first collecting or warning about pending edits. Validation errors are rendered after every major section; the same failed render recreates inputs from saved content. A selected named difficulty candidate can also cause the preview/play content to differ from the recipe editor. The explanatory sentence acknowledges that split, but does not make it easy to reason about. Results are mostly raw JSON.

**Consequence.** A user can believe a change had no effect, repeat work unnecessarily, lose their typed values, or draw a tuning conclusion from the wrong configuration. This is more damaging than visual density: it undermines confidence in the tool's purpose.

**Improvement.** Track editable working state explicitly and show a compact local state: “Unsaved changes,” “Saved locally,” or “Tested revision.” **Save & play** should validate and persist the current working values, then launch precisely that snapshot. On failure, retain input values, focus the invalid field, and show its explanation nearby. Preserve edits across workspace navigation. If switching authored revisions requires abandoning work, offer a concrete save/discard choice. Default tests to the current draft; keep alternate recipe comparisons in advanced test setup with an unmistakable source label. After testing, return to the same editing context with a short outcome and the revision actually tested. Keep full evidence expandable.

**Acceptance check.** Change a count, click Save & play, and verify the resulting configuration/report has that count. Enter an invalid count and verify the value remains visible with a nearby error. Navigate between waves with pending edits and verify no silent loss. Load an old result and verify it cannot silently become the active editable revision. After a new edit, the prior result must be labeled as belonging to an earlier revision until retested.

## Practical V2 information architecture

Use three task-oriented destinations, not a stack of equally weighted panels:

1. **Tune** — choose encounter/wave, adjust common values, see rhythm, save and play. This is the default and complete everyday path.
2. **Test** — manual play, recent outcomes, replay, and an expandable automated-test setup. A user should not need this destination to perform the basic Save & play flow.
3. **Experiments** — named drafts, revision history, saved scenarios/evidence, import/export, and deliberate promotion instructions. Technical identity and provenance remain available here.

A compact persistent context line should state the encounter, wave, draft name, and save/test state. Avoid a second competing context selected through a named difficulty recipe in the normal view. Navigation should use readable encounter and wave names; move stable IDs into details or copy controls. Do not put inactive capabilities behind dozens of disabled inputs.

Within Tune, begin with the selected wave's enemy groups and a few meaningful controls: enemy count, time between arrivals, and wave-end crowns. Keep encounter starting crowns available under a clearly labeled **Encounter settings** disclosure because its scope spans waves. Put batches, stagger, repetition, ability cycles, and movement multipliers under **More timing options** for the selected group. Do not show every packet expanded by default. Global defender/enemy/rule changes belong in a separate advanced section with an explicit scope notice; retain JSON access for specialists.

This is a presentation and workflow change. Do not invent an “easier/harder” slider that silently changes multiple simulation parameters, replace capabilities with placeholders, or discard reproducible evidence.

## Suggested review gate

Before adding features, test this one continuous task: open a fresh workbench, choose a wave, change a common value, play that exact change, return, understand the result, and revise again. Then verify that advanced packet edits, scenario overrides, replay, automated comparisons/search, import/export, and promotion remain reachable and behave as before. Capture matched desktop and narrow-view screenshots of the default flow and its error/result states. Do not treat a prettier initial screenshot as proof that edit state and tested state agree.
